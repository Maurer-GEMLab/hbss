# Contributing

Read `HBSS-dev-plan.md` first — this file is the short operational version of it.

## Where code goes

**`experiments/`** — the research sandbox. Push directly to `main`. Not
installed, not linted, not type-checked, not tested, not reviewed. This is
where you find out whether a method works, and it is deliberately free of
process so that finding out stays cheap.

Convention: `experiments/YYYY-MM-initials-slug/`, with a `README.md` giving
five lines — question, what I did, result, verdict, where the code went. Copy
`experiments/_template/`.

**`packages/`** — the library. Pull request, one approving review, green CI.

### The graduation rule

Code moves from `experiments/` to `packages/` when, and only when:

1. it has a test,
2. its interface is stable, and
3. someone other than the author has read it.

Graduations are reviewed once a month. Nothing in `packages/` may import from
`experiments/` — it isn't installed, so it can't.

## The dependency rule

`hbss` must never import torch, directly or transitively. The `core-isolation`
CI job installs it alone into a torch-free environment and runs the full suite.

Learned models are consumed as **exported artifacts** — predicted noise fields
in the tile store, candidate probability tables for the sampler — never as live
imports. If you find yourself wanting to `import torch` inside `packages/hbss`,
the design has drifted; raise it rather than working around it.

## The stub policy

Every component owned by someone who is not yet available gets a minimal,
working `v0` built by whoever is. The `v0` is deliberately unambitious: it
exists to unblock what is downstream and to establish the interface the real
implementation will satisfy.

This means the project never blocks on one person's availability, and whoever
picks the component up inherits a working system with tests rather than an
empty directory. Replacing a `v0` is unambiguously the new owner's
contribution. See `HBSS-dev-plan.md` section 5.1.

## Testing

Tests are tiered by runtime. Mark anything slower than a unit test:

```python
@pytest.mark.statistical   # tier 1: ~5 min, every PR
@pytest.mark.integration   # tier 2: ~20 min, nightly
@pytest.mark.benchmark     # tier 3: hours, weekly
@pytest.mark.needs_data    # requires $HBSS_DATA_ROOT
@pytest.mark.needs_gpu
```

Bayesian inference code fails silently — it produces smooth, plausible, wrong
posteriors that ordinary unit tests will not catch. Two techniques carry most
of the load, and new inference code is expected to be covered by both:

- **Dense-solve reference.** For a linear-Gaussian model the joint posterior is
  one multivariate Gaussian; build its block-tridiagonal precision matrix,
  solve directly for small `T`, and require the fast path to match to ~1e-9,
  marginal likelihood included.
- **Simulation-based calibration.** Draw from the prior, simulate, infer, rank.
  Non-uniform ranks are a proof of a bug.

For learned components: overfit-one-batch, a leakage guard asserting spatial
and temporal blocking in splits, and calibration thresholds as export gates.

## Provenance

Every run writes a `run.json`: git SHA and dirty flag, resolved config, input
data manifest hashes, RNG seeds, package versions, host and accelerator, wall
time. No result goes in a manuscript without one.

Data never goes in the repository. Register datasets in
`packages/hbss/src/hbss/io/registry.yaml` and fetch with `hbss-fetch`. Test
fixtures are ≤ 5 MB and generated by `hbss.simulate` where possible.

## Decision records

Non-obvious choices get a one-page ADR in `docs/decisions/`: context,
decision, alternatives, consequences. Copy `ADR-0000-template.md`.

This is how someone joining in 2027 learns why the inner loop is written the
way it is, and how the methods paper's software section gets written without
archaeology.

## Commits and reviews

- Small, focused commits; imperative subject lines.
- Reviews should take a day, not a week. If a PR is sitting, ping in the
  weekly meeting.
- Approving a PR means you read it, not that CI passed.
